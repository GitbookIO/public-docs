# Monorepos

Use site-wide Git Sync to sync multiple spaces from one repository and branch. Map each space to its own directory in `gitbook-docs.yaml`.

### How site-wide Git Sync works

The site’s **Project directory** sets the Git Sync installation directory. `gitbook-docs.yaml` lives there. If you leave it empty, GitBook uses the repository root.

In `gitbook-docs.yaml`, each space has a `content.directory`. That directory contains the space’s `.gitbook.yaml`, `README.md`, `SUMMARY.md`, and content files.

For an overview of these files, see [Content configuration](content-configuration.md).

### Map spaces to directories

Use **Content mapping** in the Git Sync panel to map each space. GitBook saves the mapping in `gitbook-docs.yaml`.

Directory paths work as follows:

| Path     | Meaning                                          |
| -------- | ------------------------------------------------ |
| `./docs` | A directory inside the site’s Project directory. |
| `/docs`  | A directory from the repository root.            |
| `docs`   | The same as `./docs`.                            |

For example, this repository maps three spaces:

```
/
  gitbook-docs.yaml
  documentation/
    .gitbook.yaml
    README.md
    SUMMARY.md
    .gitbook/
      assets/
        logo.png
  developers/
    .gitbook.yaml
    README.md
    SUMMARY.md
  changelog/
    .gitbook.yaml
    README.md
    SUMMARY.md
```

This `gitbook-docs.yaml` maps each space to its directory:

{% code title="gitbook-docs.yaml" %}
```yaml
$schema: https://api.gitbook.com/gitbook-docs.yaml
site:
  structure:
    - type: space
      key: documentation
      title: Documentation
      path: documentation
      content:
        directory: ./documentation
    - type: space
      key: developers
      title: Developers
      path: developers
      content:
        directory: ./developers
    - type: space
      key: changelog
      title: Changelog
      path: changelog
      content:
        directory: ./changelog
```
{% endcode %}

### Keep space content self-contained

Each space only syncs the directory assigned to it. GitBook doesn’t automatically share content or assets between mapped directories.

Keep every referenced asset inside its space’s mapped directory. If several spaces need an asset, add a copy to each directory or reorganize the repository.

The `.gitbook.yaml` `root` setting controls where GitBook reads content within that space’s mapped directory. It doesn’t make sibling directories available.

### Move a mapped directory

Move a space’s content by updating its files and mapping together:

1. In the repository, move the space’s content files and assets.
2. In `gitbook-docs.yaml`, update that space’s `content.directory`. Leave its `key` unchanged.
3. Commit both changes in the same commit.

{% hint style="info" %}
If GitBook imports before both changes exist, the mapped space can appear empty.
{% endhint %}

{% hint style="danger" %}
**Don’t rename the `key` to match the new directory.** Keys and directory names are independent. Changing a space’s key replaces the space with a new one that has a new space ID, and restoring the original key doesn’t bring the old ID back. See [Keys identify your spaces](content-configuration.md#keys-identify-your-spaces).
{% endhint %}

Keys generated by GitBook — `space-1`, `space-2` — don’t reflect directory names, and there’s no benefit to keeping the two aligned.

### Multiple sites, spaces, and branches

Several sites can sync from one repository, and different spaces can map to different directories, branches, or repositories. What you can't do is give one space two different Git Sync targets.

#### A space has one Git Sync configuration

Git Sync is configured per space, not per site. A space's repository, branch, and directory travel with the space wherever it's used.

{% hint style="danger" %}
**Reusing a space across two sites doesn't give you separate environments.** If the same space appears in a production site and a test site, both sites publish the same space, and that space syncs to a single branch. Committing to that branch to test a change updates production too.
{% endhint %}

To run a test environment against a different branch, use separate spaces — one per environment — rather than reusing one space across both sites. Each space then has its own Git Sync configuration, and the two can't affect each other.

#### Site-wide mapping takes precedence

When a site's `gitbook-docs.yaml` maps a space, that mapping is the space's effective configuration. It replaces any configuration set on the space itself.

This matters when a space was synced individually before being added to a site's content mapping: after the site maps it, the site's repository, branch, and `content.directory` apply. If the two point at different directories, the space's content moves to the site's mapped directory, which can leave duplicated content and assets behind at the old path.

Before adding an individually synced space to a site's content mapping, check that the site's mapped directory is where you want that content to live. See [Content configuration](content-configuration.md#configure-the-site-with-gitbook-docs.yaml).

#### Supported combinations

| Configuration                                            | Supported                                                                                  |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Several spaces in one site, each mapped to its own directory | Yes. This is the standard monorepo setup described above.                                  |
| Two sites syncing from the same repository                | Yes, provided each site maps its own spaces. Give each site its own **Project directory**. |
| Spaces in one site on different branches                  | No. A site's content mapping uses one repository and branch for every space it maps.       |
| One space serving two sites with different branches       | No. The space has one Git Sync configuration. Use separate spaces instead.                 |
| A space on its own repository or branch, outside the site mapping | Yes. Remove it from the site's content mapping and configure it individually.       |

### Use individual space Git Sync

Use individual space Git Sync when a space needs another repository or branch. For example, use it when a private space must sync separately.

Remove the space from the site’s content mapping first. Then configure Git Sync from that space.

To configure the space, follow [Enabling GitHub Sync](enabling-github-sync.md) or [Enabling GitLab Sync](enabling-gitlab-sync.md). In the scope step, select **Space Git Sync**.
